## 0. 巡检口径

**方法**：Playwright Chromium 1440×900 实跑；每项走主路径 + 异常输入 + 页面级中断（刷新/后退/Esc/取消/重复提交）。进程级中断（杀 daemon）单独串行执行，避免污染分区取证。

**裁定（用户已定）**：

1. **现状体检**：只对有真实入口的功能评级；未实现项单列「范围声明」，不计入第三部分断点。
2. **严重度主轴**：信任损伤 > 任务中断成本 > 学习成本。
3. **证据标准**：每行必须有截图或可复现的交互/接口记录；没观察到的写「未观察到，待确认」。

**评级约定**：「部分」只授予**已证实的破损**（某条已验证的路径走不通或结果错误）；因取证纪律或环境缺失**未覆盖**的子项记「未观察到」，不拉低整体评级。因此 E3 整体为 Y（已验证路径全部通过，仅 DeepSeek/ComfyUI/埋点的写入按纪律未测），而 C3 为 部分（拖拽排序已证实无效）。

**覆盖对象**：`docs/spec/page-inventory-v1.md` 的 54 项。注意这 54 项是**验收对象清单，不是 54 条路由**——27 项有独立 `page.tsx`，27 项是浮层/子组件/状态族（详见该文件与 `apps/web/src/app` 的对应关系）。

**本次未验证**（原因）：

- 受控 AI 成功路径（真实 DeepSeek 响应 → IR → 审批）：凭据未注入；且传输层已被证伪（§3.1）。
- ComfyUI 出图成功路径：本机 8188 无服务（`/image/probe` 报「未检测到本地 ComfyUI 服务」）。
- 市场装载成功路径（D4）：市场索引为空（`/market/query` → `state:"empty"`、`total:0`），无资产样本；`/market/load-plan` 对不存在 ID 返回 404。
- 桌面壳（Electron）：未取二进制、未运行。
- A 区 15 项（主窗口壳/标签栏等）：按清单口径属 P6 参照，不在本次范围。

**三处环境性阻断（不影响线上用户，但影响任何接手者）**：

1. `pnpm --filter @dforge/daemon dev` 在 Node 22.16 直接崩：`ERR_UNKNOWN_FILE_EXTENSION ".ts"`。README 写「Node ≥ 22」，实测 22.16 不剥类型；本次用 `node --experimental-strip-types` 起 daemon。
2. `http://127.0.0.1:3000` 下不水合：现象确凿（`anyReact=2`、点击全无反应，且与 `/_next/hmr` 握手 `ERR_INVALID_HTTP_RESPONSE` 并存）；换 `localhost:3000` 后 `anyReact=127`、`[HMR] connected`。**因果机制未定位**（「Next 16 dev 的 origin 校验」是最可能的假设，仓库未配置 `allowedDevOrigins`），但现象与修法不受影响：README 第 38 行教桌面壳 dev 态装 `127.0.0.1:3000`，按该路径会得到死页。首批 127 截图已隔离为 `_invalid-127/`，不计证据。
3. `next dev` 启动即警告「React 18 support is deprecated in Next.js 16」（当前 `react 18.3.1` + `next 16.4.1`）。

## 2. Agent / 自动化特有维度

判断依据 = 代码 + 运行时观察。受控 AI 的成功路径未能实跑（无凭据），因此结论以「当前实现能证明什么」为准；凡只能从代码推断的，标明「代码级」。

### 2.1 意图可见性 — **缺失**

- **执行前**：AI 抽屉只有一个文本框和一个「生成」按钮（`AiDrawer.tsx:147-159`）。没有「我理解你要做 X」「将影响这 3 个图层」「可逆/不可逆」的任何预览。提交即发请求。
- **执行中**：四步是过程名（排队/模型生成/校验/编译），不是意图。用户看不到正在改哪些节点，因为没有节点在被改。
- **执行后**：结果区只渲染 `content: string`（`AiDrawer.tsx:199-205`）；契约 `AiChatResponse` 里没有 IR、没有 ops/diff、没有事务 id（`packages/contracts/src/ai/index.ts:64-74`）。抽屉也没有任何「插入画布/应用到文档」的回调（全部 props 只有 `onConfigureCredentials`）。
- **唯一面向 AI/自动化写入的审批界面**是 MCP 确认条（tool/caller/审计号/可展开 diff，`McpConfirmBar.tsx:121-167`）。注意区分：版本历史也有对比视图（C14/F10），但对象是版本快照，不是 agent 提案。而 MCP 确认条全仓没有任何非测试代码派发它监听的事件（`mcp-host.tsx:58`），普通用户永远看不到。

> 结论：AI 路径上，用户既不知道 agent 打算做什么，也不知道它做了什么——因为 agent 事实上没有改任何东西。

### 2.2 渐进透明 — **缺失**

- 所有任务走同一套四步，不区分「改一个圆角」与「重构整页」；没有风险分级，也没有随信任变化的解释深度。
- 五种降级原因（`no-credentials / upstream-error / timeout / rate-limited / invalid-response`，`contracts/ai/index.ts:35-40`）在 UI 上被压成一个「本地模板」角标。`degradedReason` 存进了状态但**从未被渲染**（全仓 grep 只在 `steps.ts` 出现，`AiDrawer.tsx` 不读）。
- 更严重：降级文案声称「降级结果：由本地模板生成，展示形态与在线结果一致」（`zh-CN.json:695`），而实测 `POST /ai/chat` 的降级响应 `content: ""`。代码级核实：`degradedResponse` 的 `content = partialContent ?? ''`（daemon `ai/client.ts`），**全仓不存在任何「本地模板」生成器**——五种降级原因的内容都是空串或上游已吐出的部分文本。设置页也重复同一句「本地模板兜底」（`E3`）。

> 结论：既不透明，也不渐进；降级态还给了用户一个不存在的承诺。

### 2.3 转向控制 — **名义存在，实际不可达**

- AI 运行中没有「取消/中止」按钮；唯一的中止方式是关闭抽屉触发 unmount → abort（`use-ai-run.ts:38-44`）。用户不能在生成中途改方向或限范围。
- AI 路径没有批准/拒绝节点，因为不产生可审批的变更。
- MCP 路径的机制本身是对的：一次性 token、倒计时、批准/拒绝、超时失效（`confirm.ts:43-57,87-94`）。但我实测：**确认 200 后确认条 150ms 内整体消失**（F9），审批人看不到「已批准/未产生真实写入」；daemon 重启后旧 token 返回 403（我的进程测试），而恢复文案「需重新发起 dryRun 提案」指向一个普通用户没有的入口。
- 且它展示的 diff 恒为 **1 条占位 op**（`stub.ts:88-100`：「桩实现：真实 diff 由 P5 网关按 Design IR 生成」），即使有人到达也无法据此判断影响面。

> 结论：有杠杆的节点不存在；存在的那个够不到，且反馈会消失。

### 2.4 能力边界 — **运行时状态较好，产品承诺错误**

- **做得好的部分**（本产品最成熟的一类界面）：设置页连通性状态片、诊断面板自检（版本/环境/连通性/日志）、ComfyUI 未启动横幅与缺模型清单、AI 未配置横幅 +「去配置 key」建议（`AiDrawer.tsx:141-145,86-95`）。「服务在不在」说得很清楚。
- **说错的部分**：
  - 首页首屏最显眼的「用 AI 开始设计 / 描述你想要的画面，AI 助手会给出初稿与图层结构」（`zh-CN.json:35`）——实际只回一段文字，不产生图层。
  - 抽屉副标题「用自然语言描述修改」暗示会修改文档——实际不改。
  - 错误面漏英文技术串：AI `Failed to fetch`、保存 `保存失败：Failed to fetch`、市场「无法连接本地服务：TypeError: Failed to fetch」。中文界面里出现浏览器内部错误，且没有「本地服务未启动/去启动」这类可执行解释。

> 结论：状态性边界说得清；能力性边界说错了，而后者恰好决定用户会不会信任它。

### 2.5 失败恢复 — **机制最强的一维，但有三个死点**

- **强**：
  - AI 失败落在具体步骤 + 错误文案 + 重试保留上次输入；流提前关闭有兜底「流式通道提前关闭」（`use-ai-run.ts:85-88`）。
  - 出图：OOM 降档重试、缺模型清单、重新探测（`ImagePanel.tsx:67-122,208-221`）。
  - 保存：失败态 + 原因；我实测杀 daemon →「保存失败：Failed to fetch」→ 重启 → 再点保存 →「已保存」，4 个节点无损（`artifacts/ux-audit/part2/interrupt-*.png`）。
  - 版本：对比 → 确认恢复 → 回滚前自动保存（C14/F10 实测）。
  - 市场：断网 → 重试 → 恢复（F14）。
- **死点**：
  1. AI 重试必然失败——CORS 未变，重试是死循环。
  2. MCP 结果态被立即清空；重启后 token 失效且无法自行重新发起。
  3. 错误文案是浏览器原文，英文且无下一步；保存失败没有自动重试，也没有「服务已断开」的状态提示（只有顶栏一行字）。

> 结论：恢复机制在，恢复体验不在——问题不在能力，在文案与自动恢复。

### 2.6 小结

| 维度 | 判定 | 一句话 |
|---|---|---|
| 意图可见性 | 缺失 | 没有计划、没有影响面、没有变更清单 |
| 渐进透明 | 缺失 | 一套流程走到底，五种降级原因压成一句「本地模板」 |
| 转向控制 | 名义存在 | 正确的审批机制在 MCP 里，但用户到不了；结果态还会消失 |
| 能力边界 | 部分 | 服务状态说得清，产品能力说错了 |
| 失败恢复 | 较强 | 机制齐全，但 AI 死循环、MCP 无出口、错误文案不可读 |

## 3. 三个体验断点

按「信任损伤 > 任务中断成本 > 学习成本」排序。

### 3.1 断点一：AI 生成在浏览器里必然失败，失败信息还不可读

- **触发场景**：编辑器 → 点「设界 AI」→ 输入任意指令（例如「给首屏加一个主按钮，并把圆角统一为 8」）→ 点「生成」。
- **用户感受**：等几秒，看到「排队 失败」「Failed to fetch」和一排等待中的后续步骤；点「重试」——还是失败。用户无法判断是没配 key、网络问题，还是软件坏了。降级横幅明明写着「建议去配置 key」，但真正的原因不是这个。
- **证据**：
  - 浏览器 console：`Access to fetch at 'http://127.0.0.1:4318/ai/chat' from origin 'http://localhost:3000' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header`（`artifacts/ux-audit/part2/ai-degraded-submit.png`；F4 三次复现）。
  - curl 对照：同一端点**非流式**响应带 `access-control-allow-origin`，**流式（`stream:true`）响应一个 CORS 头都没有**（localhost / 127.0.0.1 / `null` 三种 Origin 均无）。
  - 根因：SSE 走 `raw.writeHead` 直写 socket（`apps/daemon/src/routes/ai.ts:32-37`），绕过了 `cors.ts:87-110` 在 `onRequest` 里用 `reply.header` 加的 CORS 头。AI 抽屉只走流式（`client.ts` 的 `chatStream`）。
- **不修的后果**：第二支柱「受控 AI」在第一次接触就失败；daemon 精心实现的降级响应、建议清单、本地模板**全部没有机会呈现**；桌面壳（`Origin: null`）同样拿不到 ACAO。这不是「AI 不够聪明」，是「AI 根本不通电」。

### 3.2 断点二：承诺「初稿与图层结构」，交付的是一段不可用的文字

- **触发场景**：首页（首屏最显眼）「用 AI 开始设计 / 描述你想要的画面，AI 助手会给出初稿与图层结构」→ 打开 AI 助手 → 生成成功（假设 3.1 已修）。
- **用户感受**：要的是图层，给的是文字。没有「插入画布」「应用」「查看 diff」任何一个动作，这段文字只能看、不能用。四步里的「校验」「编译」还都打了勾——用户会以为内容已经被校验、被编译成图层了。
- **证据**：
  - 文案：`apps/web/messages/zh-CN.json:35`。
  - 契约：`AiChatResponse` 只有 `content: string`，没有 IR/ops/事务（`packages/contracts/src/ai/index.ts:64-74`）。
  - UI：结果区只渲染文本，抽屉没有任何 apply 回调（`AiDrawer.tsx:199-213`）。
  - 假步骤：`stream.ts:144-149` 在收到 `done` 帧**之后同一拍**推进 `validate → compile`，背后没有校验或编译发生。
  - 链路：daemon 的 `ai/client.ts` 不 import `@dforge/engine`，全仓没有「AI 文本 → Design IR」的编译路径。
- **不修的后果**：核心差异化承诺落空，用户会把「设界 AI」归类为聊天框；一旦后续接入真实写操作，这个「假校验」会污染信任基线——用户会带着「系统校验过了」的错觉去批准变更。这比不显示步骤更危险。

### 3.3 断点三：命令面板（P0）裸奔，⌘K 入口与清单不一致

- **触发场景**：编辑器按 `⌘/`（或主菜单「命令面板 ⌘/」）；按清单在首页/设置按 `⌘K`。
- **用户感受**：左上角冒出一个没有边框的裸输入框，命令列表直接压在画布与图层面板上，没有遮罩、没有居中卡片；首页和设置按 `⌘K` 毫无反应；长按 Ctrl 的速查卡跑到视口外（`y=916`，视口高 900），完全看不见。
- **证据**：
  - 截图 `artifacts/ux-audit/E/E7-editor-open.png`（裸输入框 + 压住编辑器的命令列表）。
  - `.dfg-cmdk` 在已加载样式表中规则数为 0；`features/command-palette/command-palette.css` 有 25 条规则，但**全仓没有任何地方 import 它**（唯一相关行是 `editor-shell.css:354` 的一句注释「样式已迁至…」）。
  - 键位：清单 E7 写「⌘K」，实现注册的是「⌘/」（`register.tsx:42`），且只在编辑器内；首页/设置无入口。
- **不修的后果**：P0 级高频入口看起来像半成品，一屏就能击穿用户对「这是一个能用的编辑器」的判断；速查卡等于不存在。这个问题只需要一行 import 与一次键位/入口对齐，投入产出比最高。

## 5. 一句话总结

这是一个**编辑器内核扎实、AI 承诺落空**的 P0 产品：画布、Inspector、版本回滚、保存恢复、空/错/加载态都经得起真机操作（35 项 Y），但第二支柱「受控 AI」在浏览器里连请求都发不出去（3.1），即使修通也只回一段没有出口的文字（3.2），而它承诺的审批与审计在界面上无处可寻。最该先修的是一行 CORS 头与一行 CSS import——两者都是分钟级修复，却分别决定了「AI 能不能通电」和「命令面板像不像成品」。

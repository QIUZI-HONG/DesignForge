# 24: follow-up · 跨文档粘贴的组件来源不可证：id 相撞会静默重绑到无关组件

**What to build:** 让「粘贴后的实例指向哪个主组件」这件事**可证**——现在它靠 id 是否在目标页出现来推断，而 id 相同不代表同源。二轮复核（CL-2）实测：把 A 文档的实例粘进 B 文档，若 B 页里**恰好存在同 id 的主组件**（哪怕语义毫无关系），`settleComponentRefs`（`packages/engine/src/clipboard/clipboard.ts:517-555`）的「目标页快照里被引用节点在位」分支就判定引用有效、原样保留 `componentId`；实例从此挂在无关组件上。这个形状**两道写侧门都拦不住**：引擎 `validatePage` 的 `missing-component` 只查存在性（`packages/engine/src/scene/validate.ts:451-461`），web 写前 `validateDocument` 与 daemon `canvas-integrity.ts` 同口径——**存在但张冠李戴**在三层都是合法形状。后果是**静默的**：保存前后盘上逐字节相同（没有任何东西变化提示），用户只在实例「变了样子/跟着改错内容」时才发现，且此时已经落盘，撤销也只在会话内有效。

**这是既有缺陷，不是本轮 diff 引入的**：票 17 的落定口径（`settleComponentRefs`）把「引用不可证即降级」做成了默认安全，但它证明的是**存在性**，不是**同一性**（`clipboard.ts:533-535` 的存在性证明即本票要替换掉的那一步）。本票不重开票 17。

**可达性（据二轮实测，定级按此，不许写成「正在丢用户数据」）**：

- **偶然相撞概率≈0**：`ClipboardPayload`（`clipboard.ts:54-59`）不带**文档身份**（只有 `sourcePageId`），id 由 `createIdFactory` 按会话递增生成，跨两份**独立创建**的文档撞到同 id 的机会极小。
- **确定相撞的一条腿是活的**：同一份 `.dfg` 的两个拷贝（用户「复制一份文档」/ Git 检出两份 / 导入备份后再新建）共享全部 id——从 A 粘贴到 B **必撞**，且撞上的就是那个「同名同 id 的同源组件」，看起来还是对的，只有其中一份被改过才暴露。
- **会话侧不清盘**：`clipboardPayload`（`apps/web/src/features/canvas/state/session.ts:308`）在 `copy` 时写入（`:812`）、`paste` 时取用（`:819`），**从不因文档切换而清空**；`adoptDocument`（`apps/web/src/features/canvas/workspace/workspace-session.ts:129/192-202`）复用同一会话对象载入另一份文档——于是「在 A 里复制 → 切到 B → 粘贴」是**当前就能走通**的路径，不需要任何新特性落地。
- **降级分支在生产永不触发，帮不上忙**：`session.ts:829-834` 恒传 `page`，所以「无目标页快照 → 存在性不可证 → 降级为普通帧」这条只在单元测试里活着；「载荷内主组件随复制」也不成立——`copyNodes`（`clipboard.ts:88-135`）只收所选子树，**不把外部主组件嵌进载荷**。`componentRemap` 在 `apps/web` 的非测试文件里出现 **0 次**，等于没有调用方在用「显式断言目标引用」这条正路。

**Blocked by:** None (can start immediately)

**Status:** ready-for-human（判据里含产品决策：跨文档粘贴要不要按「来源不可证」一律降级，还是引入显式来源标识）

blockers:

- [ ] **先定来源标识的载体**（人类决策，不由实现者代答）：`ClipboardPayload` 加 `sourceDocumentId`（+ 主组件指纹）？还是 `copyNodes` 把被引用但未选中的主组件**一并嵌进载荷**（自包含，粘贴时在目标页重建组件并 remap）？两条路的数据后果不同：前者要求目标页存在同指纹组件才放行；后者会让「复制一个实例」在目标文档里**新建主组件**（用户可见的语义变化，需在工单里写明是否接受）
- [ ] 载荷自检与落定判据同步改口径：存在性证明（`clipboard.ts:533-535`）升级为**同一性证明**（同文档来源 + 同指纹），不成立走既有的「降级为普通帧」分支；判定条件改动必须同时落到引擎 `validatePage` 的注释口径与 daemon `canvas-integrity.ts` 的范围自述（两者只查存在性，本票**不得**偷偷让 daemon 承担同一性校验——那里是 opaque JSON 口径）
- [ ] 会话侧清盘判据：切文档 / `adoptDocument` 之后 `clipboardPayload` 与 `clipboardPort` 的旧载荷**不得跨文档可用**（要么清空，要么带来源校验后拒用），并把这条做成用例可断言的状态，而不是靠「用户不会这么做」
- [ ] 覆盖面（真形状，端到端）：
  - 同一文件的两份拷贝（同 id 同语义）互粘 → 断言引用**仍是**那个组件（不许误伤这条最常见路径）；
  - 两份独立文档**人造同 id** 且语义不同（宽度/子树不同）互粘 → 断言按选定语义处理（一律降级为帧，或重绑到新建的随载荷组件），**绝不**静默挂到无关组件上；
  - 「A 复制 → adoptDocument 载入 B → 粘贴」这条活腿单独一条用例；
  - 引擎层：`clipboard-hierarchy.test.ts` 现把「目标页有同 id 节点即保留引用」钉成期望行为，本票要显式改这份期望并说明改判依据。
- [ ] 序列化兼容：载荷新增字段属于**线格式变更**，旧载荷（无来源字段）读入时的口径必须显式（视为不可证 → 降级，并给出提示），不得让旧数据打开即报错

**红线（本票的验收底线，违反即未完成）：**

- 不得靠「放宽 `settleComponentRefs` 的存在性判定」把误绑改掉——那会把票 17 的降级强度一起降下去；只能**加证明**，不能**减校验**。
- 不得用 id 命名规则（前缀/长度/随机度）当同一性判据。
- 三态退出码：2 不算过；只放宽超时，不放宽断言。
- 不得改 `packages/engine/__snapshots__/fixed-document.json` 与其 `.sha256`（冻结真值；本票动载荷形状时尤其容易顺手重冻，见票 17 完成记录第 1 条）。
- 不得为了让用例通过而在 daemon 里解析设计语义（`canvas-integrity.ts` 的范围口径见票 23「待人工决定 1」）。
